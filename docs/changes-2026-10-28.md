## 1. Protected All tasks view

Priority: Medium. No source screenshot.

- Keep a stable, unfiltered All tasks view that users can always return to.
- Protect its name, filter and deletion. Sorting and visibility/display
  preferences remain editable; users can still edit its tasks/folders.
- For older collections where the original view was renamed, filtered or
  deleted, ensure the protected unfiltered view exists and preserve customized
  old views separately. Do not silently destroy their customizations.

## 2. Accessible Create action

Priority: Medium. Source image 1: short creation dialog above a wide keyboard.

- Retain the existing bottom Create action.
- Add a second top-right Create action for new tasks and folders when the layout
  is short or keyboard-constrained, on any platform. It is not an unconditional

## 3. Linked-appearance counter

Priority: Medium. Source image 2 marks the intended small counter area.

- Show a compact `Links: N` on tasks and folders only when N >= 2.
  Use the small right-hand area beneath the row menu marked in source image 2.
- N is the number of hierarchy paths where the item appears in the collection,
  including paths through linked ancestors. It is not just direct incoming links
  and is not multiplied by the number of filtered views rendering the item.
- Example: T has only one direct parent F, but F appears under both A and B.
  T has two collection appearances and shows `Links: 2`.
- This helps users understand that changing/completing a shared item changes
  that item everywhere. Coordinate the counter with section 13's removal rules.

## 4. Sorting and drag insertion

Priority: Medium. Source image 3 marks between-sibling insertion targets.

- Offer Manual, Title/alphabetical, Due date and Priority. Automatic sorts have
  ascending/descending directions. No creation-date/status sort was requested.
- Each parent task/folder has a separate sorting choice in each view. The top
  level has the same four options, also separately configurable per view.
- There is one shared manual order across views. Switching an automatic mode
  does not turn the underlying manual order into a different per-view order.
- During automatic sorting, folders come first, then tasks; sort each group by
  the chosen key. Items without dates stay after dated items in either direction.
  None-priority items similarly stay last within their group in either direction.
- Equal primary values use alphabetical title as the secondary key, then manual
  order for identical titles.
- Support clear between-item drop indicators as well as inside-parent targets.
  Manual ordering persists after dragging.
- A between-sibling drop while automatically sorted automatically changes that
  parent in the current view to Manual. Use the currently displayed order as
  the starting point, apply the drop, and save the resulting shared manual order.
  Do not first restore the previous manual order or add a switch-mode prompt.

## 5. Direct-child summary indicators

Priority: Medium. Source image 4 marks spare space on parent cards.

### Metrics and defaults

Use direct child tasks only, not tasks at deeper levels. Defaults:

| Indicator | Default | Meaning |
| --- | --- | --- |
| Total | On | Number of eligible direct child tasks |
| Completed / total display | Optional | Replaces the plain count with `Total: completed / total` |
| High priority | On | Number of eligible direct children with High priority |
| Medium priority | Off | Equivalent Medium count |
| Low priority | Off | Equivalent Low count |
| Next due date | Off | Earliest eligible due date today or later; ignore overdue dates |

Normal total, priority counts and next due date follow both the view's rules and
the current Unfinished/Completed tab. The completed/total display is the explicit
exception: include both completion states matching the view's rules, regardless
of tab. For three unfinished and two completed matching children, it displays
`Total: 2 / 5` on either tab, replacing rather than accompanying the plain count.

Show zero for every enabled total/priority counter. Use compact numbers for
totals and a small priority icon plus number for each priority count. When all
three priorities are enabled, stack their icon/count pairs vertically without
increasing the task card's height, while keeping them readable. Use section 8's
icons. Do not run a disabled indicator's metric computation.

### Defaults and overrides

Each indicator inherits independently through these layers:

1. Collection-wide defaults in Settings.
2. Optional shared defaults for the parent, across views.
3. Overrides for that parent in the current view.

Changing a parent indicator in one view leaves other views unchanged. Later
changes to defaults propagate only where that individual indicator has no
explicit override; customizing one indicator does not freeze the entire set.

## 6. Tag selection and recent popularity

Priority: Medium. Source image 5 shows the confusing tag-assignment area.

- Show all selected tags above a light dividing line.
- Below it show up to N popular unselected tags and Select other. N defaults
  to 5 and is configurable in the collection settings. Selected tags do not
  consume these suggestion slots.
- Select other opens a search bar and multi-select tag list. Done applies the
  picker's choices to the item draft; Cancel discards that picker operation.
  The item editor's own Save/Cancel still determines whether assignments commit.
- Rank tags by recent manually committed assignments within the collection.
  Do not count automatic assignments, tags carried by copying, or cancelled
  draft assignments as manual popularity events.
- Usage influence fades gradually: by default an assignment has half its
  influence after three days. This period is also configurable in Settings.
  Tags recently assigned often rise; their advantage fades when use stops.
- Existing collections start without usage scores. Use alphabetical ordering
  until actual manual assignments establish popularity; do not invent history
  or seed scores from existing tag-assignment counts.

## 11. Item drafts, cancellation and stable cursor

Priority: High, together with item 10. Source images 11 and 12 show notes being
edited and the cursor moving to the end during autosave.

Text editing must preserve the cursor/selection rather than resetting them as
autosave or model refresh occurs. Keep an isolated, recoverable item draft.
Text can be retained privately during editing but must not prematurely become
the live shared item, appear in other placements or publish as committed edits.
Tag/date/priority changes and automatic-completion changes also remain in that
cancellable draft until it is committed. This resolves the source document's
initial distinction between immediate fixed-value changes and text changes.

### Editor action policy

| Action | Approved result |
| --- | --- |
| Save on existing task/folder | Validate, commit draft and close the editor |
| Cancel on item edit | Discard the cancellable draft |
| Tap outside an existing editor | Save and close if valid; otherwise stay open and show what needs fixing |
| Back / Escape with unfinished edits | Ask Save / Discard / Keep editing |
| Switch desktop task, view or collection with unfinished edits | Ask Save / Discard / Keep editing before switching |
| Back / Escape or switching without unfinished edits | No save/discard prompt |
| Tap outside new-item creation | Ask Create / Discard / Keep editing |
| App closes/crashes before saving an edit | Offer restore or discard of the separate unfinished draft on next launch |

Keep editing cancels the attempted departure/switch. Tasks and folders share
this editing, exit-prompt and draft-recovery behavior.
An explicit task/view/collection switch follows its prompt policy rather than
being silently treated as an ordinary save-on-outside-tap.

### Separate operations

- Visibility settings apply immediately and are outside the cancellable draft.
- A tag created from the editor remains in the collection after item Cancel;
  its cancelled assignment to that item is discarded.
- Task/folder conversion is separate: resolve unfinished edits, then confirm
  and apply the conversion.
- Linking, copying as part of the new Link/Copy operation, unlinking and deleting
  must not silently commit unfinished edits. The owner explicitly chose separate
  Link/Unlink/Delete operations: first resolve unfinished edits, then perform
  the operation with its normal confirmation behavior.

### Preserve document-save safeguards

An item draft is separate from the existing private document working copy and
external-file publication flow. Committing a draft uses the shared command and
save/recovery policy; do not bypass file-identity checks, pending-save barriers,
conflict handling or recovery ownership. Cancel must not attempt to undo shared
item changes that were already prematurely dispatched. Keep recovered drafts
associated with the correct item/collection and avoid silent stale overwrites.

## 13. Additional linking, copying and removal rework

Implementation candidate: [behavior, compatibility and acceptance](link-copy-removal.md).

Added explicitly during clarification of item 3; no separate priority was assigned.
These later decisions supersede the earlier either-Unlink-or-Delete menu and the
intermediate proposal to give linked parent appearances different child lists.

### Appearances and removal actions

- Two or more collection appearances: offer both Unlink and Delete.
- One appearance: offer Delete only.
- Delete removes the underlying task/folder everywhere, regardless of which
  appearance initiated it. Always confirm deletion. With multiple appearances,
  explain deletion everywhere and tell the user to choose Unlink for local removal.
- When deleting a parent, delete children only if they have no surviving
  appearances. Preserve children that also appear under surviving parents.
- Ordinary Unlink removes the selected placement, carrying its subtree out of
  that occurrence, while other appearances remain untouched.

### Blocked child Unlink in a linked parent

Linked parents retain shared child lists. A child may not be unlinked in a way
that changes the children of the parent's other linked appearances. For example,
A → F → T and B → F → T do not become different child lists for shared F.

When the user requests that child Unlink:

1. Explain why it cannot be done directly and identify the blocking linked parent.
2. Offer to cancel or replace the selected linked parent occurrence with a full
   independent copy of the parent and its descendants.
3. For this special operation, force full depth and independent copies for every
   appearance, regardless of the normal Copy defaults below.
4. Delete the selected copied child and its copied descendants. Do not move them
   to top level or leave an extra independent copy beside the linked parent.
5. Keep the original parent, child and their other appearances untouched.

This is a compound operation whose final state must preserve those guarantees,
including when linked ancestors make an apparently local edit affect other paths.

### General Link/Copy popup

- Change the linking action to Link / copy task to, supporting the task/folder
  hierarchy. Search destinations by title/name; include tasks, folders and Top level.
- First dropdown: Link or Copy, default Link.
- Second dropdown: copy depth, enabled only for Copy. Include available child
  depths for the source hierarchy and always Create copies of all child tasks.
- Bottom buttons: Cancel and one action matching the mode, Link to or Copy to.
  This supersedes the earlier three-button design.
- An info button expands popup height and reveals two short explanatory
  sentences: one for what linking does and one for what copying does.
- Link excludes the source itself and every descendant to prevent cycles.
- Copy allows the source itself or a descendant as destination only when all
  descendants are copied. Automatically select All descendants, lock the depth
  dropdown, and display the reason. Do not offer a cycle-producing partial copy.

### Copy depth and repeated items

Copy mode always creates a new source item. It defaults to copying the source
only and linking its original children. For Trip → Packing → Passport:

| Choice | Result |
| --- | --- |
| Source item only (default) | New Trip linked to original Packing and its original hierarchy |
| Through direct children | New Trip and Packing; new Packing links original Passport |
| All descendants | New Trip, Packing and Passport |

By default, copy each unique item once and preserve its internal links in the
new hierarchy. The new item is separate from its original. An unchecked
Make every appearance independent checkbox turns this reuse off when checked,
so repeated appearances become separate new copies at the copied levels.

If Trip contains Passport directly and also Packing → the same Passport,
copying through direct children creates new Trip, Packing and Passport. The
new Packing reuses the new Passport, even though that occurrence is deeper
than the limit; it does not link back to the original Passport. Reuse of a copy
created within the chosen depth takes precedence at that boundary. Do not
mutate an original linked subtree's contents to manufacture copied references.

Copy operations must use fresh identities and a finite source snapshot, preserve
the original hierarchy, and remain acyclic. Creating a copy inside its own source
must not recursively copy the newly attached result. Existing deleted-container
view-rule warnings and document save/recovery safeguards remain applicable.

## 14. Migration safety prerequisite

Added by the owner after dependency review because existing collections are
already in everyday use, including on the father's phone. The shared foundation
is now implemented as a candidate; see [migration safety](migration-safety.md).
The requirements below remain the acceptance contract. Physical upgrade
acceptance is pending; later feature conversions still need explicit plans.

### Detect before modifying

- Decide whether the update needs to migrate an existing file/store. UI-only
  changes need no artificial data migration. Apply this safety gate to automatic
  transformations of existing contents/settings too, even without a schema bump.
- Detection must not itself invoke a write-on-open migration before backup.
- Identify the exact source and its version/state. Treat an external collection,
  a retained working copy with unpublished edits, and recovery metadata as
  different data; a backup of one is not proof that the others are protected.
  Preserve each existing store that will be converted and all pending edits.

### Verified backup first

- For collection files, create the backup beside the original, or use an
  authorized backup folder where the provider requires it. This is the owner's
  selected location, rather than an app-private collection backup.
- On Android a retained file URI may allow access only to that file, not creation
  of a sibling. Obtain the necessary folder authorization/destination before
  migrating. Once configured, create the backup in the background without asking
  the user to manually copy the file.
- Make a consistent snapshot of the source: do not copy a changing SQLite file
  while ignoring pending journal state or active writes. Flush/close or use an
  appropriate snapshot mechanism without prematurely migrating the source.
- Complete and verify the backup before applying a migration. Read it back and
  verify completeness/content against the intended source snapshot, preserving
  its pre-migration format so it remains usable for recovery. Verification must
  not trigger an in-place migration of the backup itself.
- Give backups distinct names/identities; never overwrite an earlier valid
  backup on a later upgrade or retry. Retain the pre-migration backup after the
  migration rather than deleting it immediately upon success.
- If permission, space, provider availability, writing or verification prevents
  creation of a verified backup, stop. Explain what is needed and offer retry
  after resolution; do not modify existing data or silently choose another
  storage location to bypass the requirement.

### Stage, validate and publish

- Migrate a separate working candidate after the backup is verified. A failure
  while transforming/validating the candidate leaves the original untouched.
- Validate the migrated result before replacing a usable source: include IDs,
  tasks/folders, text, tags, dates/priorities, completion, relationships/order,
  views/preferences, and the new defaults/metadata as applicable. Preserve
  existing customizations and pending data, not merely a loadable empty file.
- Publish through the shared save coordinator and platform adapters, retaining
  fresh file-identity/content-baseline checks and read-back verification. Do not
  bypass an external edit or disconnection because a migration is in progress.
- Use atomic replacement where supported. Android provider writes are not
  universally atomic: if final publication fails or is interrupted, stop further
  writes, keep the verified backup and recoverable candidates, and explain
  recovery options. Restoring/reopening a backup must preserve existing identity
  and conflict safeguards rather than blindly overwriting a newer external edit.
- Record enough durable stage state to distinguish completed migration from
  interruption on restart. Retry/recovery must not erase the original backup,
  duplicate migrated data or silently treat partial publication as success.

### Automatic failure diagnostics and recovery access

- On failure at any migration stage, including backup/preflight, automatically
  create and persist a diagnostic log file;
  its creation must not depend on the user first pressing Export. On restart,
  detect an interrupted migration and record/report that failure as well.
- Include useful allowlisted information: application/build and OS versions,
  source/target format versions, migration stage, timestamps, sanitized error
  codes, non-content validation summaries and anonymous references correlating
  the attempt, backup and candidate. Keep task text, notes, tag names, raw SQL
  values, full paths/URIs and credentials out of default exported diagnostics.
- Use private diagnostic storage and user-initiated Export/share access so the
  owner can supply the file for debugging. No automatic upload. Keep failures
  understandable without requiring the user to read technical logs.
- Expose the backup/recovery location and safe recovery actions. If diagnostic
  persistence itself fails, still stop unsafe writes and report that logging
  failed; never claim a log or a verified backup exists when it does not.

### Required verification before a data-migrating release

- Upgrade representative collections from the currently distributed format,
  including linked hierarchies, custom views/settings, pending edits and recovery.
- Verify the backup can be reopened and contains the pre-migration state.
- Exercise missing backup-folder grants, denied access, low storage, failed
  backup writes/read-back, candidate transformation/validation failures, app
  interruption, external changes and failed final publication.
- Verify failure retains recoverable data, creates useful redacted logs when
  storage permits, offers export/recovery and permits a safe retry. Success must
  retain the backup and publish the complete validated data exactly once.
- Confirm physical upgrade/data preservation on the Pixel/GrapheneOS and Samsung
  alongside appropriate Windows/Fedora checks. Host tests alone are not proof
  of preservation on either family's phone.
